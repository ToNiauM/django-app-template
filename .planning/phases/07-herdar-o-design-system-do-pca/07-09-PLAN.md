### Onde o helper mora, e por quê

`core/tests/contraste.py` — **dentro do sistema gerado**, não em `.template-tests/`.
Razões, nesta ordem:

1. `.template-tests/` está em `_exclude` do `copier.yml` (linha 24): nada dali chega ao
   derivado. Um helper lá deixaria todo sistema gerado sem a guarda de contraste.
2. Os testes Django (`core/tests/`, `apps/*/tests/`) precisam dele para medir a família
   derivada de `COR_PRIMARIA` em runtime — e só eles têm `core.tema` importável.
3. As suítes de `.template-tests/` conseguem carregá-lo por caminho (`importlib`), então
   uma única implementação serve às duas famílias de teste.

`core/tests/` já é pacote (`__init__.py` presente) e o discovery do Django é
`test*.py` — um módulo chamado `contraste.py` **não** é coletado como suíte.

### Contrato do helper (assinaturas exatas)

```
luminancia_relativa(hex_: str) -> float
    # WCAG 2.x: canal/255, linearização ((c+0.055)/1.055)**2.4 para c > 0.03928,
    # senão c/12.92; L = 0.2126*R + 0.7152*G + 0.0722*B

contraste(hex_a: str, hex_b: str) -> float
    # (Lmais_claro + 0.05) / (Lmais_escuro + 0.05) — simétrico por construção

tokens_do_input_css(caminho: Path | None = None) -> tuple[dict[str, str], dict[str, str]]
    # Devolve (claro, escuro). `claro` = o bloco :root.
    # `escuro` = {**claro, **overrides do bloco [data-tema="escuro"]} — o bloco escuro
    # só declara o que tem valor próprio, e quem não está lá HERDA o claro
    # (input.css:93-96). Sem essa fusão, medir --cor-destructive no escuro daria KeyError.
```

`hex_` aceita `#rrggbb` (6 dígitos). Entrada fora do formato levanta `ValueError` —
o helper é de teste, falhar alto é o comportamento certo.

### O regex cego do G-05 — o que está errado e o que passa a valer

`.template-tests/test_07_tokens.py:224`:

```
r"\btext-([a-z0-9]+|\[[^\]]+\])\b"      # o \b depois de ] torna o 2º ramo inalcançável
r"\btext-(\[[^\]]*\]|[a-z0-9]+)(?![\w-])"   # alternativa específica primeiro + lookahead
```

Comportamento exigido do regex novo, string a string (é isto que o teste da guarda assere):

| Entrada | Grupo 1 esperado |
|---|---|
| `class="text-[13px] font-bold"` | `[13px]` |
| `class="font-bold text-[13px]"` | `[13px]` |
| `class='text-[20px]'` | `[20px]` |
| `class="text-2xl"` | `2xl` |
| `class="text-ink-2"` | *(nenhum match — é cor, o lookahead recusa o hífen)* |
| `class="text-white"` | `white` *(match, mas não é tamanho conhecido → ignorado pelo gate)* |

Observação para não gerar confusão com a tabela do CR-04: com o lookahead, a string
artificial `text-[13px]x` deixa de casar. Isso é correto — não existe classe assim; o
antigo `\b` só casava lá por acidente.

### Por que `TEXT_CLASS_RE` tem que subir para o nível do módulo

Hoje o regex é uma variável **local** dentro de
`test_templates_so_usam_as_seis_chaves_da_regua_tipografica`. Um teste da guarda que
declarasse a própria cópia do regex não provaria nada sobre o gate. Suba
`TEXT_CLASS_RE`, `TAMANHOS_TAILWIND_CONHECIDOS` e a varredura para o módulo, e faça os
dois testes consumirem os mesmos objetos.

### `fontSize` em `theme.extend` vs `theme` (WR-14)

`theme.extend.fontSize` **acrescenta** ao default: `text-2xl` … `text-9xl` continuam
existindo e gerando regra, e a única barreira é o gate. Movendo `fontSize` para `theme`
(irmão de `extend`, não dentro dele) o Tailwind **substitui** o mapa e deixa de gerar
qualquer coisa fora das 6 chaves — o teto vira propriedade da build.

`colors`, `borderRadius` e `fontFamily` **continuam** em `extend` (precisam somar ao
default: `text-white`, `bg-red-600`, `rounded-full` de terceiros etc. seguem em uso).
`_extract_block(config, "fontSize:")` não depende de aninhamento — os testes existentes
continuam válidos.
