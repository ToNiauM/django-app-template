### Contrato do banco de ensaio (`.template-tests/ensaio_django.sh`)

O script é **ferramenta**, não suíte: o nome não começa com `test_` de propósito, para que
`python3 -m unittest discover -p 'test_*.py'` e a lista de suítes do README não o
confundam com uma regressão.

**Superfície de linha de comando** — subcomando obrigatório, exatamente estes:

| Subcomando | Efeito | Saída em stdout |
|---|---|---|
| `subir` | garante que existe um banco saudável (renderiza e sobe se preciso) | 4 linhas: `ENSAIO_DESTINO=…`, `ENSAIO_PROJETO=…`, `ENSAIO_PORTA=…`, `ENSAIO_URL=http://127.0.0.1:<porta>` |
| `porta` | idem `subir`, silencioso | só o número da porta publicada |
| `url` | idem `subir`, silencioso | só `http://127.0.0.1:<porta>` |
| `destino` | idem `subir`, silencioso | só o caminho absoluto da cópia |
| `testar <alvo…>` | roda `python manage.py test <alvo…> --noinput` **dentro** do container `web` da cópia | a saída do Django, e o **mesmo código de saída** |
| `executar <cmd…>` | `docker compose exec -T web <cmd…>` na cópia | a saída do comando, e o mesmo código de saída |
| `compor <args…>` | `docker compose --project-name … --env-file .env <args…>` dentro da cópia (para `up -d web`, `logs`, `images`) | a saída do Compose |
| `derrubar` | `down --volumes --remove-orphans`, remove `dados/` via container root e apaga a cópia e o estado | nada |

Sem subcomando, ou com subcomando desconhecido: uso em **stderr** e saída **2**. Todo
diagnóstico (render, build, espera de healthz) vai para **stderr** — stdout carrega só o
que a tabela promete, para que `$(bash .template-tests/ensaio_django.sh url)` seja usável
direto dentro de outro comando.

**Estado e reúso.** A cópia vive fora do repositório, num diretório derivado de
`${TMPDIR:-/tmp}`, do uid e de um hash do caminho absoluto do template (dois checkouts
diferentes nunca colidem). Junto dela ficam a porta, o nome do projeto Compose e a
**impressão digital** do working tree.

A impressão digital é o sha1 de um **fluxo canônico de pares `caminho`+`conteúdo`**,
construído a partir de
`git ls-files -z -co --exclude-standard -- . ':!.planning' ':!.template-tests'`
(rastreados + não rastreados não ignorados, exceto planejamento e as próprias suítes —
nenhum dos dois entra na árvore gerada, porque `.template-tests` e `.planning` estão no
`_exclude` do `copier.yml`; `copier.yml` em si **entra**, e é o que faz o plano 07-03
invalidar o banco ao mexer no `_skip_if_exists`).

Três regras que o contrato **precisa** fixar, porque esta fase estressa exatamente elas:

1. **O caminho entra no hash, não só o conteúdo.** Para cada caminho da listagem, em ordem
   `LC_ALL=C sort`, alimenta-se o hash com o próprio caminho, um `\0`, e depois o conteúdo
   do arquivo. Sem isso, renomear um arquivo sem mudar o conteúdo deixaria o banco de
   ensaio ser reaproveitado com a árvore errada. Esta fase renomeia arquivos; nenhuma
   dessas renomeações é de conteúdo idêntico, mas o buraco existe e é do componente do qual
   **todo** gate da fase depende.
2. **Caminho listado que não existe no disco vale `AUSENTE`, não erro.** `git ls-files -c`
   lista o que está no **índice**: um arquivo apagado com `rm` (sem `git rm`) continua
   aparecendo. Alimentar `sha1sum` com um caminho inexistente aborta o script sob
   `pipefail`, ou — pior — muda o digest por acidente. Portanto: se o caminho não é um
   arquivo regular legível, alimenta-se o hash com o caminho seguido do marcador literal
   `AUSENTE`. Assim a remoção é **determinística** e faz a impressão mudar, que é o
   comportamento correto — esta fase apaga dois arquivos rastreados.

   **O caso ausente não leva o `\0`.** O separador é justamente o que distingue as duas
   formas: presente = `caminho` + `\0` + conteúdo; ausente = `caminho` + `AUSENTE`, sem
   `\0` no meio. Se o `\0` fosse aplicado também ao caso ausente, um arquivo cujo conteúdo
   é exatamente `AUSENTE` produziria o mesmo digest do mesmo caminho apagado — e apagá-lo
   deixaria de invalidar o banco. (Um separador **distinto** do `\0` no caso ausente — por
   exemplo `\x01` — resolve o mesmo problema; o que não é aceitável é usar o mesmo
   separador nos dois casos.)
3. **Só conteúdo entra; metadados não.** Nada de `mtime`, permissão ou inode. O
   fingerprint é de conteúdo por decisão: um `touch` que não muda byte nenhum não deve
   custar um `up --build`.

**Orçamento de tempo (normativo para todos os planos da fase).** Toda mudança de código
invalida a impressão digital, e o `testar`/`subir` seguinte **recria o banco**: `copier
copy`, `docker compose up -d --build`, espera de `/healthz` (até 180 tentativas de 1 s) e
`migrate`. A primeira criação da fase inclui ainda `pip install -r requirements.txt`,
`apt-get` e `npx tailwindcss@3.4.17` no build da imagem. Isso **não cabe** no timeout
padrão de 120 s do executor. Regra:

- Todo `ensaio_django.sh subir` / `testar` / `derrubar` e toda suíte que os chame
  (`test_07_cor_runtime.sh`, `test_05_nascimento.sh`) roda com **timeout explícito de
  600000 ms** — o teto do executor.
- A **primeira** criação do banco (Task 3 deste plano, cache Docker frio) roda **em
  background** e é acompanhada por polling, porque pode passar de 600 s sozinha.
- A espera de `/healthz` fica em 180 × 1 s = **180 s de teto**, e o script imprime
  `compose ps` + `compose logs --tail=100 web db` em stderr antes de abortar. Esse teto é
  do laço, não do comando: o build que o antecede não está contado nele.
- Reúso de banco (sem mudança de código) é de segundos — é para isso que o fingerprint
  existe. O timeout longo é seguro, não obrigatório: ele só é gasto quando há recriação.
- **Fallback de estouro de timeout — vale para os oito planos da fase, não só para a
  primeira criação.** Toda mudança de código invalida a impressão, então cada `subir`/
  `testar` dos planos 07-03 a 07-07 pode virar uma recriação completa; com imagem base
  atualizada, cache do Docker podado ou `npx tailwindcss@3.4.17` refeito, uma recriação
  tardia também passa dos 600000 ms. Regra: se um `subir`/`testar` **anunciou recriação em
  stderr** e estourou o timeout, isso **não é reprovação de gate** — repita o mesmo comando
  em background com polling, exatamente como a primeira criação da Task 3, e espere o
  código de saída real. Só reprova o gate um comando que **terminou** com código diferente
  de 0. Nunca reduza escopo nem declare falha por timeout.

Regra de reúso, nesta ordem: o banco é reaproveitado **se e somente se** a cópia existe,
a impressão gravada é igual à atual **e** `curl -fsS <url>/healthz` responde. Em qualquer
outro caso o script **derruba e recria do zero**. Recriar (em vez de re-renderizar por
cima) é decisão deliberada: `copier copy` não apaga arquivo que sumiu do template, e esta
fase remove três arquivos (`tailwind.config.js.jinja`, `_nav.html.jinja` e, no update,
classes mortas) — uma cópia atualizada por cima passaria a mentir. O custo é um
`up --build` por mudança de código; o cache de camadas do Docker é global e absorve a
maior parte.

**Criação do banco**, na ordem:
1. porta livre obtida com o mesmo trecho Python de `test_05_nascimento.sh:121-128`
   (`socket.bind(("127.0.0.1", 0))`);
2. `"${COPIER}" copy --defaults --vcs-ref=HEAD` com `--data` para
   `sistema_nome=Sistema Ensaio`, `sistema_slug=ensaio`,
   `sistema_hostname=ensaio.example.invalid`, `sistema_porta=<porta livre>`,
   `sistema_banco=ensaio`, `sistema_sigla=ENS`, `cor_primaria=#1e40af` e
   `incluir_app_exemplo=true`. `cor_primaria` é **o default do `copier.yml`** de propósito:
   assim o `.env` da cópia bate com o default declarado no `input.css`, e o plano 07-04
   consegue medir a troca de cor a partir de uma linha de base conhecida;
3. guarda anti-v0.1.0: falhar se `core/static/img/logo-entidade.svg` não existir na cópia
   ou se `.copier-answers.yml` gravar `_commit: v0.1.0` — as mesmas duas asserções da
   Task 2, aqui aplicadas ao banco;
4. `cp .env.example .env` e substituição dos três placeholders (`SECRET_KEY`,
   `POSTGRES_PASSWORD` e a senha embutida em `DATABASE_URL`) por segredos efêmeros
   gerados com `secrets.token_urlsafe`, reaproveitando o bloco Python de
   `test_05_nascimento.sh:146-171`;
5. `docker compose --project-name <projeto> --env-file .env up -d --build db web`;
6. espera de `GET /healthz` com o mesmo laço de `aguardar_web` (180 tentativas de 1s), com
   `compose ps` + `compose logs --tail=100 web db` em stderr antes de falhar;
7. `compose exec -T web python manage.py migrate --noinput`;
8. gravação de porta, projeto e impressão digital.

**Nome da porta.** A variável de ambiente publicada pelo `.env` da cópia chama-se
`WEB_PORT` (`.env.example.jinja:23`), consumida por `compose.yml.jinja:41` como
`${WEB_BIND_ADDRESS:-127.0.0.1}:${WEB_PORT:-8000}:8000`. **Não existe** nenhuma variável
`SISTEMA_PORTA` — `sistema_porta` é resposta do Copier, não variável de ambiente. Quem
precisa do endereço usa `bash .template-tests/ensaio_django.sh url`.

**Ciclo de vida.** O banco **sobrevive** entre invocações de propósito (é o que torna o
gate barato depois da primeira vez). Ele não é apagado ao fim de cada comando; o plano
07-08 chama `derrubar` antes da regressão completa, para que o ensaio de nascimento
comece de um host limpo.
